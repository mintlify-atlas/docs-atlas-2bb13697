DBOO stores all application data as a connected object graph inside a single db4o `.yap` file. Rather than relying on traditional relational foreign-key joins, objects hold direct references or store string codes (acting as primary/foreign key identifiers) to link related objects. This approach leverages db4o's native object persistence while remaining compatible with Java Swing's GUI table-binding patterns.

## Relationship summary

The table below shows how each entity connects to others through its key fields. In a pure db4o object graph these would typically be direct object references; the DBOO codebase uses string codes as an alternative identifier approach that keeps GUI table binding straightforward.

| Entity | Key field | Related to | Via |
|---|---|---|---|
| `Organizador` | `cod_organizador` | `Evento` | `cod_organizador` FK on Evento |
| `Comerciantes` | `codigo_participante` | `Puesto` | `codigo_puesto` FK on Comerciantes |
| `Personal` | `codigo_perso` | `Evento` | `cod_evento` FK on Personal |
| `Publico` | `codigo_publico` | `Encuesta`, `Imagen` | `codigo_encuesta`, `codigo_sube_ima` FKs |
| `Patrocinador` | `codigo_patri` | `Persona` | `cedula_perso` FK on Patrocinador |

<Note>
  All foreign key codes are stored as `String` fields and resolved at query time using db4o's native object query (`ObjectSet`). There are no explicit join tables or relational schema files — the object graph is the schema.
</Note>
